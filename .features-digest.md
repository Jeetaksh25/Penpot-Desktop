## Plugin system
Location: penpot-source/plugins/libs/plugins-runtime/src (index.ts, lib/load-plugin.ts, lib/plugin-manager.ts, lib/create-sandbox.ts, lib/parse-manifest.ts, lib/modal/plugin-modal.ts, models/manifest.model.ts, models/manifest.schema.ts); penpot-source/plugins/libs/plugin-types/index.d.ts (154KB TS API surface); penpot-source/frontend/src/app/plugins/ (api.cljs 26KB, shape.cljs 85KB, library.cljs, grid.cljs, tokens.cljs, etc. — the ClojureScript RPC bridge); penpot-source/frontend/src/app/main/data/plugins.cljs (host state/load orchestration); penpot-source/frontend/src/app/main/ui/workspace/plugins.cljs (manager UI); penpot-source/frontend/src/app/plugins.cljs (runtime init); penpot-source/common/src/app/common/types/plugins.cljc (plugin spec); penpot-source/plugins/apps/* (example plugins: table-plugin, icons-plugin, contrast-plugin, etc.)
Plugins run inside an SES (Secure ECMAScript) sandbox loaded via `initPluginsRuntime(contextBuilder)` in plugins-runtime/src/index.ts, which exposes `ɵloadPlugin`/`ɵloadPluginByUrl`/`ɵunloadPlugin` on window. A plugin = a manifest.json (parsed by parse-manifest.ts into Manifest model with permissions like allow:downloads, clipboard:read/write) + code, loaded by load-plugin.ts -> createPlugin -> plugin-manager.ts. The plugin gets a `Context` (from @penpot/plugin-types) built per-plugin-id by the frontend's contextBuilder. UI runs in an iframe modal (plugin-modal.ts, openUIApi). The API surface is the TS declarations in plugin-types/index.d.ts; the actual implementations backing that API live in frontend/src/app/plugins/*.cljs (api.cljs dispatches shape/page/library/tokens/grid/text/font operations, building changes via app.common.files.changes-builder and dispatching app.main.data.changes). A new feature plugs in by (a) adding to the plugin-types declarations, (b) implementing the ClojureScript handler in app/plugins/*.cljs, (c) wiring it through the contextBuilder in app/main/data/plugins.cljs. Penpot's own MCP server is itself a plugin-host client (see AI subsystem).

## Fonts (Google Fonts provider + custom fonts)
Location: penpot-source/frontend/src/app/main/fonts.cljs (364 lines, the provider); penpot-source/frontend/src/app/main/data/fonts.cljs (font upload/fetch events, opentype.js); penpot-source/frontend/resources/public/fonts/gfonts.2025.11.28.json (the baked Google Fonts catalog, copied also to frontend/resources/fonts/); penpot-source/common/src/app/common/types/font.cljc (font-family schema); penpot-source/backend/src/app/rpc/commands/fonts.clj (17.8KB, custom-font storage RPC); penpot-source/render-wasm/src/fonts/ (wasm-side font shaping)
Fonts are split into three backends selected per font in fonts.cljs `load-font`: `:builtin` (Source Sans Pro, bundled, served from /public), `:google` (Google Fonts via the proxy), `:custom` (user-uploaded, stored in backend). The Google Fonts catalog is NOT fetched live — it is a pre-baked JSON (`gfonts.2025.11.28.json`) embedded as a macro (`preload-gfonts`) into `google-fonts` at compile time, so a new catalog = new JSON file + macro recompile. `generate-gfonts-url` builds `internal/gfonts/css` and `internal/gfonts/font` URLs against `cf/public-uri`; in Penpot Desktop the Rust proxy (src-tauri/src/proxy.rs) reverse-proxies /internal/ to the JVM, so Google Fonts CSS/woff2 are fetched by the backend, not the browser. opentype.js parses font files for metadata. The backend rpc/commands/fonts.clj handles chunked upload/storage of custom fonts in Postgres + object storage. A font-feature would plug in either by updating the gfonts JSON (offline catalog refresh), by adding a new provider branch in fonts.cljs load-font, or by adding a backend font-management RPC. Font family validation regex lives in common types/font.cljc.

## Realtime / collaboration (websocket + changes protocol)
Location: penpot-source/frontend/src/app/main/data/websocket.cljs (ws client to /ws/notifications); penpot-source/frontend/src/app/main/data/changes.cljs (apply/broadcast changes, 236 lines); penpot-source/frontend/src/app/main/data/workspace.cljs (59.8KB, dispatches changes); penpot-source/common/src/app/common/files/changes.cljc and changes-builder.cljc (change ops spec); penpot-source/backend/src/app/http/websocket.clj (ws server, 'notification service for file cooperative edition'); penpot-source/backend/src/app/msgbus.clj (Redis-backed pub/sub msgbus, IMsgBus protocol); penpot-source/backend/src/app/rpc/notifications.clj (publishes team/file change notifications to msgbus); penpot-source/backend/src/app/rpc/commands/files_update.clj (persists changes, runs migrations/validation); penpot-source/backend/src/app/redis.clj (Redis client used by msgbus)
Flow: the frontend opens a single WS to `<public-uri>/ws/notifications?session-id=...` (websocket.cljs `initialize`, upgraded http->ws). Edits are built as change-ops via app.common.files.changes-builder, applied optimistically in the frontend (changes.cljs), sent to the backend via the `update-file` RPC (files_update.clj), which validates + migrates + persists them and then publishes a notification through the Redis-backed msgbus (msgbus.clj pub!/sub!); the msgbus message is fanned out to every collaborator's WS by http/websocket.clj. There is NO dedicated app.realtime namespace — realtime == msgbus (Redis pub/sub) + http/websocket.clj + rpc/notifications.clj. A realtime/collaboration feature plugs in by: subscribing to a new msgbus topic in rpc/notifications.clj, handling a new :type in http/websocket.clj's recv labels, and reacting to ::message in frontend data/websocket.cljs / changes.cljs. In Penpot Desktop everything stays on localhost (proxy.rs proxies /ws/ to the JVM backend on :3449).

## Binfile import/export & design data model
Location: penpot-source/backend/src/app/binfile/ (v1.clj 26KB, v2.clj 15KB, v3.clj 36KB current 'ZIP based binary file exportation', common.clj 27KB shared processing, cleaner.clj, migrations.clj); penpot-source/backend/src/app/rpc/commands/binfile.clj (RPC entry for import/export); penpot-source/common/src/app/common/types/ (shape.cljc 31.5KB, shape_tree.cljc, file.cljc 53KB, page.cljc, container.cljc 27KB, objects_map.cljc, component.cljc, modifiers.cljc, token.cljc, tokens_lib.cljc 88.6KB, typography.cljc, text.cljc, color.cljc); penpot-source/common/src/app/common/spec.cljc; penpot-source/frontend/src/app/worker/import.cljs (frontend-side .penpot import worker)
A `.penpot` file is a ZIP; v3.clj is the current format ('A ZIP based binary file exportation'), v1/v2 are legacy importers. common.clj does the shared read/write against Postgres + object storage, runs app.common.files.migrations on import (so old files upgrade), and validates via app.common.files.validate. The in-memory data model is defined in common/src/app/common/types/*: a File has Pages; a Page has a shape-tree (shape_tree.cljc) of Shapes (shape.cljc — the central shape spec, 31KB, with attrs/geom/fills/strokes/components); components (component.cljc, variant.cljc), tokens (tokens_lib.cljc, token.cljc), typography (typography.cljc), and an objects-map (objects_map.cljc). binfile.clj RPC exposes import/export to the frontend; the frontend also has a worker (frontend/src/app/worker/import.cljs) for client-side import handling. A binfile/design-model feature plugs in by: extending the shape spec in common types/shape.cljc + updating the schema (sm) in spec.cljc, adding a migration in binfile/migrations.clj and common files/migrations, and updating v3.clj export + v1/v2/v3 import to round-trip the new field.

## Worker + rasterizer (render pipeline)
Location: penpot-source/frontend/src/app/worker.cljs (web worker entry, message dispatch, buffer/dedupe); penpot-source/frontend/src/app/worker/ (impl.cljs dispatcher, import.cljs, index.cljs, selection.cljs, snap.cljs, thumbnails.cljs, messages.cljs); penpot-source/frontend/src/app/rasterizer.cljs (11.9KB, iframe-based SVG->bitmap rasterizer); penpot-source/frontend/src/app/main/render.cljs (29KB, SVG React rendering used by worker + workspace); penpot-source/frontend/src/app/main/rasterizer.cljs (5KB, host-side rasterizer iframe manager); penpot-source/frontend/src/app/main/worker.cljs (worker spawn); penpot-source/render-wasm/ (Rust+wasm renderer: src/render.rs 167KB, shapes.rs 62KB, main.rs, state.rs, tiles.rs); penpot-source/frontend/src/app/render_wasm/ (api.cljs 105KB, serializers.cljs, deserializers.cljs, shape.cljs, wasm.cljs, text_editor.cljs); penpot-source/frontend/src/app/main/render.cljs + render_viewer_wasm.cljs; penpot-source/frontend/src/app/main/data/exports/wasm.cljs (wasm export path)
Two render paths. (1) SVG path: app.main.render renders shapes to SVG via React (react-dom/server), driven both from the workspace and from a Web Worker (app/worker.cljs) that receives `{:cmd ...}` messages (postMessage, schema in worker.cljs), with a 1ms-debounced buffer that coalesces same-cmd messages. Worker commands dispatched in worker/impl.cljs; thumbnails, snap, selection, import each have their own worker module. (2) WASM path: render-wasm (Rust compiled to wasm via emscripten, src/render.rs 167KB) is invoked through frontend/src/app/render_wasm/api.cljs (105KB) with serializers/deserializers; the workspace opts into it via features. The rasterizer (app.rasterizer.cljs) is a separate iframe process (not a worker) that serializes an SVG, loads it, and produces a bitmap (data-uri cached in a js/Map); the host side is app.main.rasterizer.cljs. A render/rasterizer feature plugs in by adding a new :cmd in worker/impl.cljs + a handler module, or a new shape renderer in app.main.render / render_wasm/serializers.cljs; for bitmap output, extending app.rasterizer.cljs.

Tauri 2 app. Plugins enabled (Cargo.toml + lib.rs run()): tauri-plugin-dialog, tauri-plugin-fs, tauri-plugin-shell. A feature that needs a local sidecar/server would either (a) spawn it with std::process::Command + silent() like the existing services and wait_for_port, or (b) add a Rust HTTP/WS endpoint inside proxy.rs; to expose it to the frontend, add a `#[tauri::command]` fn + `.invoke_handler(tauri::generate_handler![...])` (currently NONE registered — the builder has no invoke_handler). New shell capabilities require adding the plugin to Cargo.toml + lib.rs run() + a permission in capabilities/default.json.

## AI / LLM integration (MCP server + plugin bridge)
Location: penpot-source/mcp/ (README.md, project.yml, packages/{common,plugin,server}); penpot-source/mcp/packages/server/src/PenpotMcpServer.ts (19KB), PluginBridge.ts (18KB), RedisBridge.ts, NreplClient.ts, ReplServer.ts, PluginTask.ts, Tool.ts, ConfigurationLoader.ts, ApiDocs.ts; penpot-source/mcp/packages/server/src/tools/ (ExecuteCodeTool.ts, ExportShapeTool.ts, ImportImageTool.ts, ImportpenpotFileTool.ts 15.9KB, HighLevelOverviewTool.ts, PenpotApiInfoTool.ts, CljsReplTool.ts, CljsCompilerOutputTool.ts, CljCheckParentheses.ts, ReadTaigaIssueTool.ts); penpot-source/mcp/packages/plugin/ (the Penpot MCP Plugin — vite app that connects to the server via WebSocket); penpot-source/mcp/packages/common/; NO AI/LLM code in penpot-source/backend or penpot-source/frontend (grep for openai/anthropic/llm/assistant found nothing in backend or frontend sources)
Penpot's AI integration is the standalone MCP server under penpot-source/mcp, NOT part of the backend or frontend. Architecture (per README): an LLM client speaks MCP to PenpotMcpServer (built on @modelcontextprotocol/sdk, SSE + StreamableHTTP transports), which exposes tools (ExecuteCode, ExportShape, ImportImage, ImportPenpotFile, HighLevelOverview, PenpotApiInfo, CljsRepl, CljsCompilerOutput, CljCheckParentheses, ReadTaigaIssue). The server does NOT call the LLM itself — it is a tool host; the LLM is the external MCP client (Claude Desktop, etc.). The server reaches Penpot via the 'Penpot MCP Plugin' (packages/plugin, a Penpot plugin that connects back to the server over WebSocket) bridged by PluginBridge.ts, with RedisBridge.ts as an alternate channel and NreplClient.ts/ReplServer.ts for live ClojureScript eval. The key design: the LLM writes and executes arbitrary code inside the Penpot Plugin sandbox (via ExecuteCodeTool) using the Penpot Plugin API. There is currently NO config for external AI services in the backend/frontend and NO LLM HTTP client anywhere in the Penpot sources — all LLM interaction is external to the repo. A new AI feature would plug in either by (a) adding an MCP tool in mcp/packages/server/src/tools/, (b) extending the plugin bridge, or (c) if an in-app assistant is wanted, adding a new frontend panel + a `#[tauri::command]` in src-tauri that proxies to an LLM API (since the frontend is sandboxed same-origin through proxy.rs, an LLM call would need a proxy route in proxy.rs or a Tauri command).


# FEATURE: Code-to-Design AI generation (prompt + optional reference: URL, app, screenshot, or code) → custom or clone

**summary:** Penpot already ships a complete code-to-design AI stack: the standalone MCP server (penpot-source/mcp) exposes an execute_code tool that runs arbitrary JS in a Penpot-plugin sandbox, and an external LLM (Claude Desktop / Claude Code) acting as MCP client writes that JS using the Penpot Plugin API. The MCP README explicitly advertises "code-to-design" workflows, and a 27KB initial_instructions.md already teaches the LLM how to emit shapes. So "generation backend" already exists and is shared with feature 5 (prompt-only gen). This feature adds: (1) reference ingestion — screenshot→vision LLM, URL→HTML scrape, code→text — as extra LLM context, and (2) an in-app UI in the desktop shell so the user does not need an external MCP client. The reference modality only changes what is attached to the prompt; the execute_code → plugin-sandbox → app.main.data.changes pipeline is identical to feature 5. Feasibility ranking: code (trivial, text in) > screenshot (feasible, vision LLMs handle it, fidelity-limited) > URL (hardest, HTML/CSS→shape fidelity is poor and scraping is fragile). Cloning a site exactly is technically possible via vision but legally and fidelity-wise risky; "customize on reference" is the realistic target.

## risks
  - HTML→shape fidelity is low. CSS grid, absolute positioning, pseudo-elements, transforms, web fonts, and responsive layouts do not map cleanly to Penpot's board/flex/grid model. Failure mode: generated design looks approximately right structurally but wrong spacing/typography; user frustration. Mitigation: pair the HTML with a vision screenshot (Phase 3) so the LLM can also see the rendered result.
  - Screenshot→shape fidelity is bounded by the vision model's spatial reasoning. Failure mode: mis-estimated dimensions, wrong colors (color picking from pixels is weak in VLMs), missing text. Mitigation: place the screenshot as a semi-transparent reference layer the user aligns manually; treat output as a draft.
  - Cloning legality. Cloning a third-party website/app design exactly may infringe trademarks/trade dress. Failure mode: user clones a brand and ships it. Mitigation: product copy discourages exact cloning of third-party IP; default to 'customize' mode; no legal block in code.
  - Plugin tab must stay active. PluginBridge.assertPluginResponsive rejects tasks when the browser tab is frozen (PluginBridge.ts line 42). In the desktop webview the Penpot tab is the whole app, so this is less likely than in a browser, but long generations could still time out (30s default taskTimeoutSecs). Failure mode: long execute_code blocks time out mid-generation. Mitigation: raise taskTimeoutSecs for generation tasks, and have the LLM emit multiple smaller execute_code calls.
  - LLM API key handling. The frontend is same-origin-sandboxed through proxy.rs and cannot safely hold an API key. Failure mode: key leaked in bundled JS. Mitigation: keep the key in the Rust shell (env or app-data file), never expose it to the webview; all LLM calls go through the Tauri command or a /llm proxy route.
  - Node sidecar startup/PORT conflicts. The MCP server binds :4401/:4402/:4403; if a user already runs Penpot MCP locally (per README they might), the sidecar fails to bind. Failure mode: silent generation failure. Mitigation: pick the port dynamically and pass it to the plugin via the start-server message.
  - Bundling Node. The desktop app currently bundles a JRE but not Node. Adding a Node runtime ~40MB increases installer size. Failure mode: large installer, possible AV false-positives on bundled node.exe. Mitigation: pre-build the MCP server with pkg/node-sea into a single binary.
  - execute_code runs arbitrary LLM-generated JS in the plugin sandbox (SES). It is sandboxed, but a jailbreak or buggy generation could still spam shapes / exhaust memory. Failure mode: app hang. Mitigation: existing 30s timeout + a shape-count cap enforced in the orchestrator.

  - Which LLM provider? Anthropic Claude (vision + tool-use, README's reference) vs OpenAI vs a local model. Local models are explicitly discouraged by the MCP README for anything beyond trivial tasks.
  - Where does the API key come from? User-supplied via a settings dialog (stored in app-data), or hardcoded for a managed offering? Must be settled before Phase 1.

  - 'Customize vs clone' — is clone ever a first-class mode, or do we only ship 'customize on reference' and drop exact cloning? Cloning a screenshot exactly is the hardest fidelity problem and the legally riskiest.

# FEATURE: AI design generation with cloud and local models

**summary:** Generate a Penpot design (file or frame) from a text prompt using either a cloud LLM (OpenAI/Anthropic) or a local model (Ollama). The LLM produces a JSON "design spec" (frames + shapes); a shared converter turns that spec into Penpot shape maps conforming to app.common.types.shape/schema:shape and applies them through the existing changes-builder + add-shape path. The LLM HTTP call lives in a new Tauri Rust command (the frontend is same-origin-sandboxed behind proxy.rs and cannot reach external APIs directly); the command reads provider config (cloud API key / local endpoint) from a small JSON config file and returns the spec to the frontend, which renders a preview and commits the shapes. The same design-spec contract is the bridge to code-to-design (feature 7) and can be exposed as a new MCP `generate_design` tool (feature 3).

## risks
  - LLM output invalid/shape schema mismatch: model returns shapes with wrong types, missing required attrs, or absurd coordinates. Failure mode: apply-design-spec throws or commits a broken canvas. Mitigation: serde parse on Rust side + sm/check + cts/check-shape on CLJS side, drop/clamp invalid shapes, never apply unvalidated output.
  - Prompt injection / unsafe content: the model could return a spec referencing external image URLs or huge fills. Mitigation: DesignSpec subset has no URL/script fields; reject unknown keys; clamp sizes.
  - Cloud API key leakage: if the key ever reaches the frontend or is logged. Mitigation: key lives only in the Rust config file; get_config redacts; proxy.rs never sees it; never put it in a Tauri event payload.
  - Cost/latency: cloud generation can take 10-60s and cost per call. Failure mode: UI appears frozen, user billed unexpectedly. Mitigation: timeout + spinner + cancel (Phase 4), max_tokens cap, show estimated cost in settings.
  - Offline breakage: cloud provider unreachable when the desktop app is used offline (a core use case per MEMORY — bundled Postgres/Redis/JRE). Mitigation: local Ollama provider is the offline path; default to it when cloud endpoint is unreachable; surface a clear error.
  - CORS/sandbox: a naive frontend fetch to api.openai.com will fail (same-origin through proxy.rs + no HTTP capability). This is WHY the call is in a Tauri command — do not be tempted to add a proxy route that forwards arbitrary external requests (that widens the attack surface).
  - Local model capability: small Ollama models produce poor structured output. Failure mode: mostly-invalid specs, user frustration. Mitigation: reduced 'lite' schema, model recommendations in README, validation that drops bad shapes gracefully.
  - Overlap with feature 7 (codegen) and feature 3 (MCP): building three separate design-input paths diverges. Mitigation: adopt DesignSpec as the single intermediate early (Phase 1) so all three feed one spec->shapes importer.
  - Binfile v3 format drift: if Phase 5 emits .penpot ZIPs by hand, a future Penpot binfile version breaks import. Mitigation: prefer the spec→shapes path; only use binfile when the existing exporter can be used as the reference (round-trip a known file first).
  - Plugin sandbox alternative: ExecuteCodeTool applies shapes via the plugin API, which is permission-gated and sandboxed — an MCP-driven generate_design that returns JS for ExecuteCode is safer than direct changes, but slower and limited to the plugin API surface (no arbitrary shape attrs).

## openQuestions
  - Scope of generation: a single frame on the current page, a whole new page, or a whole new file? The spec supports all three, but the UI should pick one default (recommend: a new frame on the current page for MVP, whole-file for Phase 5).
  - Does the LLM call live in a Tauri Rust command (recommended) or as a new route in proxy.rs? A proxy route would require adding an HTTP client to the proxy and an allowlist of external hosts; the Tauri command is cleaner and keeps proxy.rs focused on the JVM.
  - Cloud provider default: OpenAI or Anthropic? Which models (gpt-4o vs o-series; claude sonnet vs opus)? Affects cost/quality tradeoff and the response-format strategy (json_object vs prefill).
  - Local model default: bundle nothing (require user-installed Ollama, per the no-admin/localhost-bind memory) or ship a tiny bundled model? Bundling a model conflicts with the existing bundling philosophy (Postgres/Redis/JRE are bundled, but a multi-GB model is different). Recommend: document Ollama, do not bundle.
  - Is the MCP generate_design tool a separate Phase 5 deliverable, or is the in-app panel enough for v1? The MCP path is only useful if users run an external MCP client (Claude Desktop) against the desktop app.
  - Should the design spec support flex/grid auto-layout, or only absolute positioning for v1? Auto-layout is much harder for LLMs to get right; recommend absolute positioning + manual layout for Phase 1, layout in a later phase.
  - Image fills: should the generator be able to insert images (e.g. via ImportImageTool's mechanism)? That requires uploading media to the backend (rpc/commands/media.clj) and is a big scope add. Recommend: solid fills only for v1.
  - Where does the settings UI live — a new panel, or integrated into an existing preferences/dialog surface? There is no existing settings panel in the workspace, so this may be the first one.

# FEATURE: Code export to React, Next.js, React Native and Android XML

**summary:** One-click export of a Penpot file/frame/page to runnable React, Next.js, React Native and Android XML. The codebase already contains a complete shape-tree → HTML+CSS code generator (app.util.code-gen, ~1400 lines, with full autolayout→flex/grid mapping) used by the Inspect "Code" tab and exposed to plugins via context.generateMarkup/generateStyle. There is NO "Penpot codegen plugin" type in this version (manifest only allows content/library/user/comment/clipboard permissions), so React/RN/Android emitters must be built as NEW formatters on top of the existing code-gen shape walk, surfaced as a built-in panel + export modal in the desktop app — not as Penpot plugins. The exporter/ JVM service only does SVG/PNG/PDF asset export and should stay untouched. The dead Rust codegen scaffolding under src-tauri is absolute-positioning-only and references undefined structs; it can be repurposed as a Tauri command for zip/file writes, but the emit logic should stay in CLJS to reuse the layout mapping. MVP = React (reuses the most existing code), then Next.js (wraps React), then React Native (new flex→StyleSheet formatter), then Android XML (flex→LinearLayout/ConstraintLayout).

## risks
  - Autolayout→flex mapping is already solved for web CSS in style_css_values.cljs, but React Native flex defaults differ (default flexDirection 'column' vs web 'row', no CSS grid). Grid layouts in a Penpot file will silently degrade — RN falls back to absolute positioning, Android falls back to ConstraintLayout or a flattened layout. Failure mode: mis-positioned children, overlapping views. Mitigation: detect grid layouts and emit a TODO comment + a warning in the UI; consider flattening grid to absolute as the documented behavior.
  - Fonts: Penpot uses a baked Google Fonts catalog (gfonts.2025.11.28.json) served via the Rust proxy /internal/ route. Web (React/Next) can keep @font-face URLs or embed woff2 as data URIs (ui/inspect/code.cljs already does fonts-data embedding). RN and Android need actual font files in assets/fonts or res/font — requires downloading woff2 (or ttf) through the proxy and converting/placing them. woff2 is not usable by Android (needs ttf/otf). Failure mode: missing-font fallback on mobile. Mitigation: for RN/Android, fetch via backend rpc/commands/fonts.clj and ship ttf; flag Google Fonts that lack a ttf URL.
  - Responsiveness: Penpot designs are fixed-size (absolute px). Emitting fixed px widths/heights produces non-responsive code. The dead codegen_react.rs had a 'responsive' flag (maxWidth/aspectRatio) but that's a heuristic, not real breakpoints. Failure mode: generated code looks right at one size, breaks at others. Mitigation: document as fixed-fidelity export; offer an opt-in 'responsive' flag that wraps the root in a max-width container and converts flex children to flex:1 (Phase 1 keeps it off by default).
  - SVG/path/boolean/mask/multi-fill shapes: svg-markup? returns true for these. Web React can inline the SVG; RN needs react-native-svg (extra dep + performance cost); Android needs VectorDrawable (conversion not trivial) or raster PNG. Failure mode: complex paths render as blank or as a rasterized image losing scalability. Mitigation: for RN/Android MVP, rasterize these to PNG via the existing export_shapes :png and embed as Image/ImageView; keep SVG inline only for web.
  - Components/variants: Penpot components (component.cljc) and variants should map to reusable React components, but the current code-gen emits a flat div tree with no componentization. Failure mode: duplicated code, no reuse. Mitigation: Phase 1 emits flat; add a Phase-1.5 step that detects component roots (cfh/component-instance?) and hoists them into separate React components imported by the main one.
  - Dead Rust codegen trap: codegen_react.rs/codegen_winui.rs/db.rs look reusable but reference undefined structs (DesignDocument/DesignElement/CodegenOptions) and have no autolayout mapping. A contributor who revives them compiles nothing (lib.rs has no mod decl) or, after adding mod decl, hits missing-struct errors and reinvents an inferior absolute-positioning emitter. Mitigation: explicitly delete or move to src-tauri/src/_archived/ and document the decision in code_export.rs header.
  - Tauri invoke_handler: the builder currently registers NO commands (per architecture map). Adding the first invoke_handler is a small but load-bearing change — a malformed generate_handler! macro can break the whole Tauri build. Mitigation: add one trivial command first (e.g. ping), confirm it builds and the frontend can invoke it, then add write_code_zip.
  - Plugin-bridge scope creep: extending app.plugins.api :generateMarkup to accept 'react' touches the plugin runtime and plugin-types/index.d.ts — a large public API surface (154KB d.ts). Risk of breaking existing plugins. Mitigation: ship as built-in-only first; only extend the plugin API once the built-in panel is stable, and keep the existing 'html'/'svg' path untouched.

# FEATURE: AI Agent MCP server — expose Penpot design operations to external AI agents (read selection, create/modify shapes, export, run plugins) from the Penpot Desktop app

**summary:** Penpot already ships a complete, upstream MCP server under penpot-source/mcp: a TypeScript server (packages/server) built on @modelcontextprotocol/sdk that exposes tools (execute_code, export_shape, high_level_overview, penpot_api_info, import_image) over HTTP/SSE on :4401, plus a "Penpot MCP Plugin" (packages/plugin, a Penpot plugin served on :4400) that connects back to the server over WebSocket :4402 and executes arbitrary JS in Penpot's plugin sandbox using the Penpot Plugin API. The server is a tool host only — the LLM is an external MCP client (Claude Desktop/Code). For Penpot Desktop the feature is therefore primarily integration/packaging, not a rewrite: bundle the pre-built MCP server + plugin, spawn them as Tauri child processes alongside Postgres/Redis/JVM, auto-load the MCP plugin into the running workspace so it auto-connects to the local WS bridge, and advertise http://localhost:4401/mcp to external MCP clients. Single-user local mode means no auth; the proxy's existing auto-login covers the Penpot session. Mutations flow through the plugin (live, undoable, sees current selection/page) — the same path the frontend uses. A later phase can add direct backend-RPC tools for headless/file-level operations and a stdio transport entrypoint.

## currentArchitecture
What exists TODAY and is directly reused:

1. penpot-source/mcp/packages/server/src/PenpotMcpServer.ts — an Express MCP server using @modelcontextprotocol/sdk's McpServer + StreamableHTTPServerTransport (/mcp) and SSEServerTransport (/sse). Single-user mode by default (no userToken required). Registers tools via server.registerTool. Session timeout, AsyncLocalStorage for per-request userToken.

2. penpot-source/mcp/packages/server/src/PluginBridge.ts — a WebSocketServer on :4402 that accepts connections from the Penpot MCP Plugin, correlates request/response by task ID (pendingTasks map), enforces a 30s task timeout, and detects frozen/suspended plugin tabs via heartbeats (assertPluginResponsive). In single-user mode it requires exactly one connected plugin. This is the canonical "how the MCP server talks to the running app" channel — it does NOT touch the DB or backend RPC directly.

3. penpot-source/mcp/packages/server/src/tools/* — concrete tools. ExecuteCodeTool sends a JS code string to the plugin; ExportShapeTool builds a `penpotUtils.exportImage(...)` code string and returns PNG/SVG (via sharp). HighLevelOverviewTool/PenpotApiInfoTool return static docs. ImportImageTool reads a file (gated by isFileSystemAccessEnabled). Mutations today are done by the LLM writing plugin code that calls penpot.* mutation APIs — there is no dedicated typed mutation tool.

4. penpot-source/mcp/packages/plugin/ — the Penpot plugin (manifest.json with permissions content:read/write, library:read/write, comment:read/write; plugin.ts opens the UI and routes task requests to ExecuteCodeTaskHandler; main.ts is the UI that owns the WebSocket to the server with heartbeat/reconnect). Served as static files on :4400 (vite preview / vite-live-preview). PENPOT_MCP_WEBSOCKET_URL and PENPOT_MCP_VERSION are baked in at build time via vite.config.ts define.

5. penpot-source/mcp/packages/plugin/src/task-handlers/ExecuteCodeTaskHandler.ts — runs the LLM-authored code in an async Function with {penpot, penpotUtils, storage, console} in scope; sets penpot.flags.naturalChildOrdering/throwValidationErrors during execution; base64-encodes Uint8Array results. This is the bridge from "MCP tool call" to "Penpot Plugin API call".

6. penpot-source/frontend/src/app/main/data/plugins.cljs — the host-side plugin loader. open-plugin! fetches a manifest by URL, checks permissions, and calls the global ɵloadPlugin (exposed by plugins-runtime) to load the plugin; load-plugin!/start-plugin! invoke it. This is where an auto-load of the bundled MCP plugin would be dispatched on workspace boot.

7. penpot-source/frontend/src/app/plugins/*.cljs — the ClojureScript RPC bridge that backs the Penpot Plugin API (api.cljs dispatches shape/page/library/tokens/grid/text/font ops, building changes via app.common.files.changes-builder and dispatching app.main.data.changes). Every plugin mutation lands here, then through app.main.repo as an RPC to the backend. So MCP-driven mutations automatically participate in the live workspace, undo stack, and realtime broadcast.

8. src-tauri/src/lib.rs — the Tauri shell. It already spawns long-lived child processes (Postgres via pg_ctl, Redis via redis-server.exe, JVM via java -jar penpot.jar) using std::process::Command + silent() (CREATE_NO_WINDOW on Windows), polls wait_for_port, holds Child handles in BackendState {jvm, redis} and kills them in shutdown_services on WindowEvent::Destroyed. The MCP server + plugin static server would be spawned the same way and added to BackendState.

9. src-tauri/src/proxy.rs — the same-origin reverse proxy on :1420. It already has a rpc_call helper (line ~283) that makes direct `POST /api/main/methods/{method}` transit+json calls to the JVM backend on :3449 and is used for auto-login (establish_session logs in penpot@localdesktop.com). This is the exact pattern a future "direct backend RPC" MCP tool path would reuse to call commands like get-file / update-file without going through the plugin/live workspace.

10. Backend RPC command set in penpot-source/backend/src/app/rpc/commands/*.clj, invoked by the frontend as `POST /api/main/methods/{name}` (see app.main.repo / proxy.rs rpc_call). Relevant candidates for a headless tool path: files.clj (get-file, get-files, get-project, create-file), files_update.clj (update-file — applies change-ops, persists, publishes msgbus notifications), files_snapshot.clj, files_create.clj, projects.clj, profile.clj, fonts.clj, media.clj, binfile.clj (import/export .penpot), comments.clj. ## risks
  - Plugin tab liveness: the MCP plugin runs inside the Penpot workspace webview. If the user navigates away from the workspace (dashboard view) or the webview is throttled, the WebSocket bridge dies and all MCP tools fail with 'no plugin connected' / heartbeat-stale. PluginBridge already detects this (assertPluginResponsive) but cannot prevent it. Mitigation: keep the workspace window active while an MCP session is open; surface a clear error to the LLM; consider a headless backend-RPC path (Phase 2) for tasks that don't need the live view.
  - Bundling Node + node_modules + sharp native binary can add 80-150MB to the installer. Sharp in particular is platform/arch-specific. Failure mode: installer bloat, antivirus complaints on Node.exe, sharp native module mismatch on Windows. Mitigation: build a single native executable (bun --compile) or prune node_modules to only the external deps; or drop sharp and return raw SVG / base64 PNG produced by the plugin's own export.
  - Port conflicts on 4401/4402/4403/4400 with other local apps (the user might run their own MCP server). Failure mode: Tauri spawn succeeds but the port is taken and the server errors out, or worse, the MCP client connects to a different server. Mitigation: wait_for_port on the expected port AND check the server's actual PID bound it; make ports configurable via env/settings with fallback; bind 127.0.0.1 only.
  - Concurrent edits: an LLM mutating via execute_code while the user is also editing races on the same shape. The plugin sandbox serializes (one task at a time per WS), but user-side edits and plugin-side edits can interleave in the change log. Failure mode: lost updates, confusing undo stack. Mitigation: document that LLM edits are undoable; add a 'confirm before apply' mode; serialize mutations through a single tool queue; never run mutation tools in parallel.
  - Version drift between the bundled MCP plugin (PENPOT_MCP_VERSION baked at build) and the desktop's penpot build. The plugin already warns on mismatch (plugin.ts:46-54) and treats '0.0.0' as a local build. Failure mode: subtle API incompatibility the LLM can't diagnose. Mitigation: build both from the same penpot-source checkout and pin PENPOT_MCP_VERSION to the desktop penpot version in one build step.
  - Auto-loading a plugin with content:write/library:write permissions without an explicit user consent click is a security boundary change — a loaded plugin can modify the design. Failure mode: an external MCP client (anything on localhost that speaks MCP) can mutate the open file without the user having explicitly approved the plugin this session. Mitigation: show a one-time 'Enable AI Agent (MCP) access?' consent on first boot; default OFF; document the localhost-only exposure.
  - Stdio transport (Phase 3) requires the MCP server process to be spawned by the MCP client (Claude Desktop), not by Tauri — or Tauri spawns it and the client attaches to its stdio pipes. Either way the existing HTTP server and the stdio server are different process modes; running both doubles the bridge load. Failure mode: two MCP servers both trying to use the single plugin WebSocket (PluginBridge rejects a second connection in single-user mode — see duplicate-token check). Mitigation: run either HTTP/SSE OR stdio, not both; make it a build/run flag.
  - The upstream mcp module is under active development (version 2.17 in package.json, branches mcp-prod-2.14.1 / staging). Bundling a snapshot risks falling behind. Failure mode: tool schema drift vs what LLM clients expect. Mitigation: pin a specific commit and document the upgrade path; subscribe to upstream changelog.
  - sharp native module on Windows can fail to load if the bundled libvips DLL is missing or the wrong runtime. Failure mode: ExportShapeTool crashes on first PNG export. Mitigation: verify sharp loads in the bundled node_modules before shipping; or replace sharp with a plugin-side PNG (the plugin already produces PNG bytes via exportImage) and skip server-side re-encoding.

## openQuestions
  - Bundle Node.js runtime (like the JRE) OR compile the MCP server to a single native binary (bun --compile / pkg)? Impacts installer size, build pipeline complexity, and sharp support. This is the biggest packaging decision.
  - Auto-load the MCP plugin on every workspace open by default, or behind a first-run consent + settings toggle? The plugin has write permissions, so silent auto-load is a trust decision.
  - Should mutations be plugin-bridge-only (live, selection-aware, undoable, requires open workspace) or should we also build the headless direct-backend-RPC path (file-level, no undo, works without an open workspace)? Recommendation: plugin-bridge first; add headless only if a concrete use case demands it.
  - Ports 4400/4401/4402/4403 — keep upstream defaults (simplest, matches docs) or remap to avoid collisions with a user's existing MCP server? If remapped, the plugin's baked PENPOT_MCP_WEBSOCKET_URL must be rebuilt.
  - Expose the MCP HTTP endpoint on 127.0.0.1 only (recommended, matches the no-admin/localhost-bind memory stance) or 0.0.0.0 for LAN AI clients? Security trade-off.
  - Do we need a Tauri `#[tauri::command]` surface (start/stop/status, get connection URL) for the frontend, or is the boot-time auto-start + a read-only status indicator enough? Adds invoke_handler wiring that doesn't exist today.
  - For Phase 3 stdio: should Tauri spawn the server in stdio mode and expose its stdin/stdout to an external client via a named pipe / TCP relay, or should the user run `node dist/index.js --stdio` themselves and Tauri only runs the HTTP variant? Affects whether one or two server instances coexist.
  - Version pinning: do we pin penpot-source/mcp to the same commit as the bundled penpot-source, or track upstream latest? Affects LLM tool-schema compatibility.

## risks
  - Schema/migration blast radius: every new shape attr or component-prop field touches spec.cljc, changes-builder.cljc, files_update.clj, binfile v3.clj + migrations. A missed migration silently corrupts saved .penpot files on reopen. Failure mode: files open with missing/blank properties, or fail validation entirely.
  - Token/variable model clash: Penpot's DTCG tokens are name-based string references ({foo.bar}); Figma variables are typed polymorphic values with per-mode resolution. Building per-instance mode overrides on top of name-based tokens can produce reference-resolution loops (token.cljc already only does a 1-level self-reference check). Failure mode: circular token refs crash the resolver or hang the workspace.
  - Variant property migration: today variants are parsed from component names ('Property 1=on, Property 2=off'). Promoting to typed props requires a one-way migration of every existing component; if the importer mis-parses, legacy libraries lose their variant grouping. Failure mode: variant sets collapse into unrelated components.
  - Dev Mode native codegen revival: codegen_react.rs/codegen_winui.rs/db.rs import crate::DesignDocument which does not exist — reviving them is closer to a rewrite than an activation. Failure mode: wasted effort rebuilding structs that were never finished; prefer the frontend codegen path first.
  - WASM renderer divergence: any new shape type (Section) or new interaction (smart-animate, mode-transition) must be implemented in BOTH the SVG path (app.main.render.cljs) and the WASM path (render-wasm/src/render.rs + serializers.cljs), plus the prototype viewer (render_viewer_wasm.cljs). Implementing only one leaves the other rendering blank or crashing when the feature flag flips.
  - AI in-app: shipping an LLM proxy in the desktop shell means storing/handling user API keys locally and adds a network dependency that breaks the 'fully offline desktop app' promise. Failure mode: offline launches hang on AI panel init, or key leakage through logs.
  - Realtime/collaboration: new change-ops auto-fan-out via the Redis msgbus, but large new payloads (per-instance mode overrides on big files) could spike WS traffic on localhost — acceptable for single-user desktop but matters if multi-user ever enabled.
  - Feature parity is a moving target: Figma ships new features continuously; chasing 1:1 parity is unbounded scope. Failure mode: endless catch-up with no shipping milestone.

# FEATURE: Real-time team collaboration via a relay server without storing designs on the cloud

**summary:** Add a relay-only server that forwards Penpot change/presence/pointer messages between desktop peers so multiple users can edit the same file live, while every peer persists the design only to its own local/desktop storage (no cloud persistence). The feature reuses Penpot's existing change wire format and WS message protocol verbatim: the relay is essentially backend/src/app/http/websocket.clj with its Postgres/Redis/msgbus persistence swapped for an in-memory topic fanout, and each desktop client grows a second WS connection (to the relay) alongside its existing localhost-JVM WS, routing the same :subscribe-file/:pointer-update/:file-change messages. Conflict resolution is centralized at the relay via a per-file monotonic revn sequencer (mirroring the revn checks already in files_update.clj) so all peers converge; each client applies remote commits through the existing handle-file-change -> dch/commit :source :remote path.

## risks
  - CONFLICT (correctness): two peers edit the same shape attr concurrently. MVP relay-sequenced LWW silently clobbers one edit. Failure mode: user's work disappears with no undo (remote commits arrive with :save-undo? false per handle-file-change). Mitigation: relay assigns monotonic revn so ordering is deterministic; document the ceiling; future OT lives in changes-builder.cljc.
  - REVN/VERN DIVERGENCE: each desktop persists its own revn locally (localhost backend) while the relay assigns its OWN revn sequence. The two counters drift. Failure mode: handle-file-change applies a remote commit with revn R, then the local persistence RPC also bumps revn -> local revn > relay revn -> next :publish-change rejected as stale. Mitigation: in relay mode, treat the RELAY revn as authoritative and make the localhost update-file RPC use :skip-validate or stop bumping revn locally (one source of truth). Decide before Phase 3.
  - PARTIAL CONNECTIVITY: relay unreachable mid-edit. The persistence queue buffers local commits to the localhost backend (good) but peers diverge silently. Failure mode: reconnect replays lagged changes from the history ring buffer, but if the buffer (N=256) overflowed, peers need a full snapshot sync which MVP does NOT have. Mitigation: size N per file based on edit rate; add a 'snapshot sync' path (send the whole file-data as one :add-obj burst) for Phase 5.
  - TRUST/AUTH: the relay is untrusted-ish (shared secret, anyone with it can join a room). Failure mode: a malicious peer sends malformed :publish-change that corrupts other peers' file-data (cpc/process-changes may throw or apply garbage). Mitigation: validate changes against cpc/schema:change ON the relay before fan-out (cheap); never trust the relay with persisted state — it only sees transient changes.
  - DOUBLE-APPLY / ECHO: in relay mode the localhost backend's own /ws/notifications may ALSO deliver :file-change for the locally-persisted commit (since update-file publishes to its own msgbus). Failure mode: the same change applies twice -> revn jumps 2, shapes double-added. Mitigation: in relay mode do NOT :subscribe-file on the localhost conn (only :subscribe-team), OR filter :file-change by session-id on BOTH conns. The session-id filter in websocket.clj already prevents self-echo from the SAME backend, but two backends (two desktops) have different session-ids — verify the localhost echo path carefully.
  - PRESENCE IDENTITY: SaaS presence keys off profile-id from the auth session. Relay-only peers have no shared profile-id namespace. Failure mode: two peers both show as 'penpot@localdesktop.com' (the desktop auto-login account) -> presence map collapses to one entry. Mitigation: generate a per-session display name + uuid on the desktop and send it in :subscribe-file; extend handle-presence to key by session-id (it already does) and display the chosen name. Decide the identity model (openQuestion).
  - PROXY INTERFERENCE: src-tauri/src/proxy.rs only reverse-proxies /ws/ to the localhost JVM. A relay WS to an EXTERNAL url bypasses proxy.rs (browser opens it directly) — verify the Tauri webview allows outbound WS to arbitrary hosts (Tauri 2 default CSP may block it; check tauri.conf.json csp setting). Failure mode: relay WS silently fails to connect. Mitigation: relax CSP connect-src for ws/wss in tauri.conf.json, or route the relay WS through a Rust-side relay client (tokio-tungstenite) and bridge to the frontend via Tauri events.
  - MSGbus TOPIC PREFIX: msgbus.clj prefixes topics with (cfg/get :tenant). The in-memory relay must NOT prefix (or must use a fixed tenant) or topic keys won't match between client :subscribe-file {:file-id} and server fan-out. Failure mode: no messages delivered. Mitigation: the relay's in-memory msgbus ignores prefix; verify file-id equality end-to-end.
  - DEAD CODEGEN/DB: src-tauri/src/db.rs and codegen*.rs are orphaned (lib.rs only declares mod proxy). If you reach for rusqlite persistence for relay config, you must first add `mod db;` to lib.rs and define the missing DesignDocument structs (per architecture map) OR write a fresh minimal db module. Don't assume db.rs compiles.

## openQuestions
  - Is the relay a standalone deployable service (Clojure jar / Rust binary run on a separate host) or hosted INSIDE one peer's Tauri shell (peer-as-host)? Standalone is simpler for MVP; peer-as-host avoids running a separate process but one peer going offline kills the session.
  - Identity model: do relay peers authenticate with real Penpot accounts (requires the relay to talk to an auth provider — defeats 'no cloud') or generate ephemeral per-session identities (display name + uuid)? The latter is local-first but presence has no persistent user identity across sessions.
  - Revn authority: is the RELAY's revn the single source of truth, or does each client's localhost backend keep its own? This determines whether to keep calling rp/cmd! :update-file in relay mode. Recommend: relay revn authoritative for shared files; localhost backend persists the file-data but adopts the relay's revn on each :file-change.
  - Do you want true CRDT/OT (commutative :mod-obj ops with per-attribute LWW + lamport clocks) or is relay-sequenced last-write-wins acceptable? LWW is dramatically less code but loses concurrent same-attr edits. Design tools usually tolerate LWW.
  - WebRTC peer-to-peer (data channels) with the relay as a signaling server vs. pure WS relay? P2P has lower latency for 2 peers and lower relay bandwidth, but is much more code (NAT traversal, ICE, TURN fallback). For MVP a pure WS relay is correct; revisit if relay bandwidth becomes a problem.
  - Should the relay persist a transient history buffer in RAM only (lost on restart) or on disk (survives restart, closer to 'storing designs on the cloud' which the feature explicitly forbids)? RAM-only aligns with the 'no cloud storage' requirement; on restart peers re-sync via snapshot.
  - What is the room/share model — is a 'room' just (relay-url + file-id + secret), or do you want named rooms with a directory? MVP: opaque shareable link. Named rooms need a registry service (more moving parts).
  - Does the desktop app need to work fully offline (single user, no relay) AND online (relay)? The plan assumes relay is an opt-in toggle; confirm the default-off behavior must not regress the current single-user desktop flow.

# FEATURE: Updated Google Fonts library (refreshed + broadened offline catalog, with variable-font support)

**summary:** Today the Google Fonts "library" in Penpot Desktop is a single static snapshot of the Google Fonts webfonts API v1 list, baked into the CLJS build at compile time, while the actual font BINARY files (woff2/ttf) are fetched live from Google via the JVM backend on demand. Refreshing the catalog is a one-file swap + recompile; making new fonts actually render offline requires bundling their binaries, which is the real work. Variable fonts are not represented in the v1 list format (no `axes`), so "broaden to variable fonts" means switching to the API v2 list and extending the variant model.

## currentArchitecture
CATALOG SOURCE (static, compile-time-baked):

There are ZERO `axes` fields — variable fonts are flattened to discrete numeric variants (e.g. "500","600"). ## risks
  - Offline rendering breakage is the core gap, not the catalog list. Shipping a refreshed JSON alone makes the picker show new families that then FAIL to render with no internet, because /internal/gfonts/css+font are live-fetched through the JVM. Users will see the list but invisible text. Phase 2 (bundle or cache binaries) is mandatory for an offline desktop app, not optional.
  - Catalog rename/removal breaks existing documents. render_wasm/api/fonts.cljs line 39 explicitly documents that gfonts.json churn makes font-id->uuid fall back to uuid/zero (Source Sans Pro). A blind refresh can silently re-font old files. Mitigation: diff old vs new catalog, keep a stable id mapping, or never remove families from the bundled JSON (only add).
  - Installer size. Bundling woff2 for 1900 families (even variable-only, one file each) is hundreds of MB to low GB. Must curate. The memory note about resource-glob flatten also applies: a `**/*` glob would flatten subdirs and break the <slug>/<variant> layout — use a bare dir path in bundle.resources.
  - Variable-font model change is invasive. get-variant/find-variant/find-closest-variant and the WASM serializers all assume discrete variant ids. Getting arbitrary axis values through changes-builder, the binfile round-trip, and the WASM renderer is non-trivial and risks corrupting text-shape data.
  - License. Google Fonts are OFL or Apache 2.0; both permit bundling/redistribution, but OFL requires shipping the license text. Add OFL.txt / Apache.txt alongside the bundled fonts. Some families in the catalog are under different terms — verify per-family before bundling.
  - Backend gfonts handler is in the prebuilt penpot.jar, not in this source tree. You cannot change the JVM-side gfonts CSS/woff2 proxying by editing Clojure here — you'd need to rebuild the JAR from upstream or intercept in proxy.rs. Favor the proxy.rs interception approach (Phase 2 option B) to stay within this repo's control.
  - Double JSON copies can drift. The catalog exists in both resources/fonts/ and resources/public/fonts/. Forgetting to update both ships a stale picker. Consider making one a build-copy of the other.

## docStructure
